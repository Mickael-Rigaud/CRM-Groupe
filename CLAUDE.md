# CRM Groupe — consignes pour Claude Code

Application interne de Mickael Rigaud pour piloter 4 activités (RGD Renova, BTP Expertise, La Référence Courtage, Propulsion) + modules transverses (Patrimoine, Gestion locative, Acquisition). Langue de travail : **français** (code, commits, interface).

## Stack (gratuite, sans build)
- SPA vanilla JS en modules ES, routage par hash (`#/page/param`). Aucun bundler, aucun `npm install` : les fichiers sont servis tels quels.
- Hébergement : GitHub Pages sur ce dépôt (branche `main`, racine). Un push sur `main` = mise en production (délai 1–2 min, Ctrl+F5 côté navigateur).
- Backend : Supabase (projet `crm-groupe`, plan gratuit) — Auth, Postgres avec RLS, Storage (bucket privé `documents`, URLs signées 1 h). Client `supabase-js` chargé depuis esm.sh. Chart.js vendu dans `assets/`.
- Mode démo : si `SUPABASE_URL`/`SUPABASE_ANON_KEY` sont vides dans `js/config.js`, `db.js` bascule sur un adaptateur localStorage (`crm_local_v1`) avec un jeu d'exemple (`js/data/seed.js`). Utile pour tester sans toucher à la production.

## Arborescence
- `index.html` — coquille, charge `js/app.js`.
- `js/app.js` — login, mise en page, `NAV` (navigation horizontale : bande 1 = les univers, bande 2 = les écrans de l'univers ouvert ; une page peut demander `fullBleed: true` pour masquer la date et occuper la surface — cas de RGD Renova). `renderNav()` est appelée **avant** `page.render()` : une page qui pose des commandes dans `.topbar` (classe `.embed-actions`) les voit préservées d'un rendu à l'autre. `js/icons.js` — icônes SVG des univers.
- `js/pages/*.js` — une page par fichier ; `js/pages/index.js` fait la table `pages` nom → fonction.
- `js/pages/home.js` — tableau de bord du groupe : filtre par entité (mémorisé, clé `crm_home_filtre`), tuile « Leads » qui ouvre la base de prospects de la structure (`BASE_PROSPECTS` : RGD renvoie à `#/rgd/clients`, son écran Clients désormais dans le CRM, BTP et Courtage à leur base, Propulsion à son pipeline ; en vue Groupe chaque pastille de la répartition ouvre la sienne), six indicateurs avec comparaison à la période précédente et micro-courbe sur 12 mois, entonnoir, objectifs, courbes de CA, journée, tâches, patrimoine et locatif. Styles préfixés `.tb-` dans `css/app.css`.
- Espaces par structure : **RGD Renova est en cours de reprise dans le CRM** (étape 4 du plan de migration). `#/rgd`, `#/rgd/clients`, `#/rgd/devis` et `#/rgd/paiements` sont désormais des **écrans natifs** (`js/pages/rgd-chantiers.js` et `rgd-facturation.js`, coquille partagée dans `rgd-espace.js`), servis comme BTP et Courtage ; **trois réalités de la base interdisent d'additionner naïvement les paiements**, et les taire donnerait des totaux faux avec l'air d'être justes : un paiement `annule` n'est pas de l'argent (13 lignes, 139 748 € au 21/09/2026) et n'entre dans aucun total ; un `remboursement` porte un montant **négatif**, donc encaissé et remboursements s'affichent séparément avec le net en dessous plutôt qu'une soustraction silencieuse ; et **89 paiements sur 165 n'ont aucun chantier** — ils viennent de Costructor avec une référence client seule. Ce n'est pas un défaut de la reprise, Cloudflare a le même compte, vérifié : ils comptent dans l'argent et l'écran dit pourquoi ils n'ont pas de client. Le **taux de signature** des devis se lit sur les seuls devis **tranchés** (signés + refusés/expirés) : inclure ceux en cours le ferait baisser à chaque devis envoyé. `#/rgd/soustraitants` met **la conformité avant l'argent** : un sous-traitant sans attestation de vigilance à jour, c'est le donneur d'ordre qui répond du travail dissimulé, sans décennale c'est RGD Renova qui porte le sinistre — au 21/09/2026, **11 actifs sur 13 n'ont aucune pièce enregistrée**. Une pièce absente n'est pas « à jour » mais « on ne sait pas », ce qui est pire qu'expiré puisque personne ne l'a jamais demandée : les deux sont rouges. La liste trie **les actifs d'abord, puis les plus en défaut** — c'est une liste de relances, et on ne relance pas quelqu'un avec qui on ne travaille plus. Les fichiers eux-mêmes restent chez Cloudflare (KV), seules les dates d'expiration sont reprises ; `#/rgd/agenda` (`js/pages/rgd-agenda.js`) fait exception : il ne lit pas une table `rgd_*` mais `agenda_events`, c'est-à-dire Google relu par le worker, et **il ne porte pas le bandeau commun** — celui-ci serait faux deux fois ici, puisqu'un rendez-vous se modifie dans Google Agenda et non dans l'application RGD, et que la fraîcheur n'est pas la même selon le jour. Le relevé couvre désormais **J-7 → J+30 une fois par jour**, en plus de la journée courante toutes les 30 minutes (`releverAgendasVersCrm(env, { large: true })`, worker RGD) : **un rendez-vous pris ce matin pour la semaine prochaine n'apparaît que demain**, et l'écran affiche la borne relevée parce qu'un agenda incomplet se lit sinon comme un agenda vide. La table `evenements` de D1 n'est **pas** reprise : ses 232 lignes portent toutes un `google_event_id`, c'est donc elle la copie de Google et la reprendre serait copier une copie — le commentaire contraire dans `20260921120000_rgd_accueil.sql` était faux et a été corrigé. L'identifiant d'un rendez-vous relevé **porte le jour** (`calendrier|google_id|jour`) : `push_agenda` fait un `on conflict (id) do update set day = excluded.day`, donc sans le jour dans la clé une « journée entière » de trois jours écraserait sa propre ligne et n'en laisserait qu'une. Les jours qui sortent de la fenêtre sont **vidés** par un `push_agenda` à liste vide (constante `OUBLI`), sans quoi chaque journée relevée resterait dans le CRM pour toujours. ils **lisent** les tables `rgd_*`, c'est-à-dire le relevé que le worker RGD dépose toutes les 30 minutes. **Lecture seule, et ce n'est pas un oubli** : Cloudflare D1 reste la vérité tant que l'étape 5 n'est pas franchie, une écriture faite ici serait écrasée au relevé suivant — un bandeau le dit à l'écran. `#/rgd/formations` (`js/pages/rgd-formations.js`) porte les **quatre fiches de poste** de RGD Renova — conducteur de travaux, chargé d'affaires, sous-traitance, assistante — soit 20 fiches et 57 sections, reprises du tableau de bord le 21/09/2026. C'est du **contenu rédigé, pas des données** : aucune table, aucun relevé, rien qui puisse être écrasé ; le texte vit dans `js/data/rgd-formations.js` et se corrige là. Le fichier s'appelait `btp-referentiel.js` côté Cloudflare pour des raisons d'histoire (il portait les DTU, partis dans l'espace BTP Expertise le 16/09) — renommé ici, sans quoi on chercherait ces fiches au mauvais endroit. **Piège du format** : une section porte soit `contenu` (un paragraphe) soit `puces` (une liste), et **la liste domine — 43 sections sur 57, 177 puces**. La première version de l'écran ne rendait que `contenu` : 43 titres suivis de rien, et le défaut ne s'est vu qu'en cherchant un mot qui existait six fois sans être trouvé. **Le menu de l'espace RGD est une arborescence** (`ONGLETS` dans `js/pages/rgd-espace.js`), dessinée par Mickael le 21/09/2026 : Vue d'ensemble, puis trois groupes — Base de données (Clients & prospects, Partenaires, Sous-traitants), Travaux (Chantiers, Réalisations), Facturation (Devis, Encaissements) — puis Agenda. « Costructor » et « Application RGD » ne figurent pas dans le dessin mais sont **gardés pour une raison chacun** : Costructor n'a aucune autre porte, et Application RGD mène au tableau de bord d'origine, qui reste **l'outil de saisie** tant que l'étape 5 n'est pas faite. « Formations » figurait dans le dessin mais n'existe pas encore ici : mieux vaut un onglet absent qu'un lien mort. Le **fond du menu est `#212121` pour RGD seulement**, posé via `.esp-app[data-espace="rgd"]` — la coquille est partagée par les quatre structures, et changer `ink` dans `schema.js` aurait repeint aussi les grands chiffres des indicateurs et les pastilles. L'orange actif n'a pas bougé : `--accent` de RGD valait déjà `#FD7A2D`. **`coquilleEspace` avertit en console** quand un écran désigne un onglet absent du menu : ça s'est produit sans que rien ne le signale — la vue d'ensemble déclarait `#/rgd/pilotage` quand le menu proposait `#/rgd`, et le menu s'affichait sans aucun repère marqué. **`#/rgd` est la vue d'ensemble** (`js/pages/rgd-pilotage.js`), comme la route `overview` du tableau de bord d'origine ; la liste des chantiers a reculé sur `#/rgd/chantiers`. **L'ordre de l'écran a été arrêté par Mickael le 21/09/2026** : le chiffre d'affaires de l'exercice **avec sa courbe mensuelle**, les quatre chiffres clés, puis le pipeline — la journée et les alertes ferment la page. ⚠ **La courbe montre le CALCULÉ, jamais le corrigé** : la saisie manuelle porte sur l'exercice entier, il n'existe aucune valeur par mois, et lisser la correction sur douze mois inventerait une répartition que personne n'a constatée. L'écran le dit quand les deux diffèrent. Les mois à venir ne sont pas tracés — une barre à zéro pour un mois qui n'a pas eu lieu se lit comme un mois sans activité. Pas de Chart.js ici : douze valeurs ne justifient pas de le charger sur l'écran qu'on ouvre le matin. **Le pipeline est celui du worker** (`/api/stats/pipeline-detail`), sept étapes en barres — Nouveaux prospects · À contacter · RDV planifiés · Devis envoyés · Devis acceptés · Chantiers en cours · Chantiers terminés. Il a remplacé le kanban des quatre colonnes, qui vit entier sur `#/rgd/chantiers` : sur l'accueil on veut voir où en est l'activité, pas manipuler des cartes. ⚠ **Ce n'est PAS une cohorte**, contrairement à l'entonnoir du groupe : chaque étape compte ce qui s'y trouve aujourd'hui, les nombres ne décroissent donc pas forcément et **il n'y a aucun taux de passage à en tirer** — l'écran l'écrit, sous les barres. Un nouveau prospect ne compte que s'il a un `apporteur_id`, comme dans le worker : sans lui, la ligne vient d'un import et non d'une démarche. Le nombre reste **hors** de la barre, sinon il disparaît sur les étapes basses, qui sont justement celles qu'on regarde. Chaque chiffre reprend la définition écrite dans `worker/src/routes/stats.js` **et pas une définition plus simple** : deux écrans qui affichent deux vérités sur le même chiffre valent moins que pas d'écran du tout. Deux conséquences qu'il faut connaître avant d'y toucher. **Le CA affiché est saisi à la main** : `manual_ca_ht_exercice`, `manual_ca_ttc_exercice` et `manual_clients_actifs` (table `rgd_reglages`, relevée depuis `app_settings`) l'emportent sur le calcul, parce que la reprise Costructor est incomplète et que le calcul sous-estime — l'écran montre le corrigé ET le calculé, cacher l'écart ferait croire que le CRM a compté ce qu'il n'a pas compté. **« Chantiers en cours » ne se déduit pas de `etat`** : c'est un devis signé + au moins un paiement + des travaux déjà commencés + ni marqué terminé ni entièrement soldé, ce qui exige `work_start_at` et `date_passage_termine`, colonnes ajoutées à `rgd_chantiers` au titre de cet écran. La **rentabilité** ne porte que sur les chantiers dont les coûts sont connus (une mission ST payée ou une fourniture) : un chantier sans coût saisi afficherait 100 % de marge et tirerait la moyenne vers le haut, il est écarté et non compté à zéro. L'**exercice comptable court du 1er octobre au 30 septembre**, pas l'année civile. Trois blocs de l'écran d'origine manquent et l'écran le dit au lieu d'afficher zéro : les **notes Google Keep** (jamais reprises), les **relances** et les **formations** (tables vides dans D1). `#/rgd/partenaires` (`js/pages/rgd-partenaires.js`) réunit les **apporteurs** et les **achats de fournitures** sur un même écran — un apporteur envoie du travail, un fournisseur en vend la matière, et surtout les achats tiennent en une ligne, ce qui ne remplit pas une page. L'écran montre **deux comptes d'apports** : « Rattachés » compte les fiches `rgd_clients` qui désignent vraiment ce partenaire (`apporteur_id`, repris au rang 6), « Déclarés » est `nb_prospects_manuel`, saisi à la main. Un écart entre les deux n'est pas un défaut du CRM : c'est une saisie optimiste ou un rattachement oublié. Jusqu'au rang 6 l'écran annonçait que le CRM ne savait pas rattacher un apporteur — c'était vrai, mais la raison n'était pas celle qu'on croyait : **le lien existait dans D1 depuis le début, il n'était simplement pas relevé**. Ces cinq partenaires vivent dans `rgd_apporteurs` et **non** dans `organisations`, bien que ce soit le bon modèle final : le relevé réécrit ce qu'il envoie à chaque passage et écraserait une saisie faite à la main dans la base de contacts — le passage vers `organisations` appartient à l'étape 5. `#/rgd/realisations` (`js/pages/rgd-realisations.js`) montre les **31 réalisations publiées sur rgdrenova.fr** et les **21 images du carrousel** d'accueil. Attention au piège de comptage : côté Cloudflare, `realisations` et `carrousel` ont **une seule ligne chacune**, et cette ligne est un document JSON — j'avais d'abord proposé de ne pas les reprendre en lisant « 1 ligne ». **Un compte de lignes ne dit rien quand le contenu est un blob.** Le relevé déplie le document en lignes (le JSON porte déjà la structure catégories → projets → images, rien n'est inventé), et ces deux tables-là sont **remplacées et non accumulées** : la source est un document complet republié entier, donc un projet retiré du site doit disparaître, ce qu'un `on conflict do update` ne ferait jamais. Le garde-fou est une condition `> 0` dans `push_rgd_partenaires` — **une charge vide ne vide pas la table**, sans quoi un JSON illisible effacerait trente et une réalisations sans bruit. Un témoignage n'est compté que s'il a un texte : le site en pose un partout, presque toujours vide avec cinq étoiles, et cinq étoiles sur un texte vide ne sont pas un avis. À l'inverse des règlements de sous-traitants, **une fourniture sans chantier entre quand même** (`deal_id` à null) : un règlement n'a pas de sens sans son sous-traitant, un achat de 7 000 € en a un même si son chantier arrive au passage suivant. **Le rang 6 n'était pas ce que le plan annonçait.** Il disait « Costructor et Meta Ads, 1 279 lignes » : `costructor.js` fait **87 lignes** de chaque côté, et **Meta Ads n'est pas un écran** — c'est `clients.source = 'meta_ads'` plus onze colonnes `meta_*`. Le vrai reste à faire était ailleurs : `push_rgd` envoyait douze colonnes de `clients` et en laissait **vingt** de côté, celles qui font d'un contact un dossier commercial. Elles vivent maintenant dans **`rgd_clients`** et **non** dans `contacts`, qui est partagée par les quatre structures — lui ajouter `meta_adset` ou `nature_travaux` ferait porter à BTP Expertise et au courtage vingt colonnes qui ne les concernent pas, et le relevé écrirait dans la table où tout le monde saisit à la main. Les champs Meta sont en **colonnes** et non en jsonb (on voudra grouper par campagne et compter par mois, ce qu'un blob ne fait pas), sauf `meta_form_data` dont la forme dépend du formulaire. `#/rgd/costructor` (`js/pages/rgd-costructor.js`) montre la santé de la recopie Costructor → tableau de bord, d'où viennent de proche en proche tous les chiffres de l'espace : **quand un devis « n'arrive jamais », la réponse est là**. Les 25 lignes **écartées volontairement** (2 contacts, 23 devis, avec leur motif) y figurent au même rang que l'état : ce sont des décisions, pas des pannes, mais invisibles elles coûtent une heure de recherche. Le **journal est tronqué aux cent derniers passages** — 292 lignes côté Cloudflare et ça grossit ; le CRM est une fenêtre sur la santé de la synchro, pas son archive. `#/rgd/app` garde l'application d'origine en iframe (`js/pages/rgd.js`, `CONFIG.RGD_DASHBOARD_URL`) pour les douze écrans pas encore repris ; l'onglet disparaîtra quand ils l'auront tous été. Le routeur suit le même schéma que BTP et Courtage : `#/rgd/<clé>` → `pages['rgd_' + clé]`, à défaut `rgd_home`. `urlRgd()` et `CONFIG.RGD_VUES` servent encore à viser un écran interne de l'application ; `#/rgd/prospects` est conservé comme alias de l'écran Clients, pour qu'un ancien lien continue de marcher ; `js/pages/btp.js` regroupe les écrans de BTP Expertise (`#/btp`, `/base`, `/dtu`, `/facturation`, `/mails`) ; sa base de données s'ouvre sur l'onglet **« Nouveaux leads »**. **« Nouveau lead » et « prospect » désignent les mêmes personnes** : ce qui les sépare est le moment, pas la nature. Un prospect reste dans la pile tant que **l'entretien d'appel n'a pas eu lieu** — étapes `lead` et `rdv1`, déclarées par `ACTIVITIES.btp.avantEntretien` dans `schema.js` et lues par `estNouveauLead()`. **Une seule définition**, partagée avec `moveStage` : dès que l'affaire quitte ces étapes, `promouvoirClient()` (`deal.js`) **passe son contact en `Client`** — sans quoi il sortirait de la pile sans reparaître nulle part, l'onglet « Prospects » ayant disparu. On ne redescend jamais : reculer d'une étape ne déclasse pas un client. Une activité qui ne déclare pas `avantEntretien` n'a pas cette notion et rien ne change pour elle ; seul BTP Expertise sépare sa base en deux. **Un lead entre dans la pile par trois chemins** : le formulaire du site, l'apport d'un partenaire ou d'un courtier (`referrer_org_id` / `referrer_contact_id`), ou la saisie à la main (bouton « + Nouveau lead », qui ouvre `dealForm` — une affaire neuve naît à la première étape du pipeline, donc dans la pile). **L'onglet « Prospects » a été supprimé** : il désignait exactement la même population, « Nouveaux leads » le remplace — avec lui sont partis les pastilles d'origine par canal et `ORIGINES`, qui ne servaient qu'à lui. **Les trois onglets se suivent dans le temps et ne se chevauchent jamais** : « Nouveaux leads » = affaire ouverte avant l'entretien ; « Clients » = affaire ouverte après l'entretien, le dossier vit ; « Dossiers clos » = plus aucune affaire en cours — gagnée, perdue, ou aucun dossier. Un cinquième onglet, **« Archivés »**, porte les fiches mises de côté (contacts **et** organisations, les deux natures y cohabitent : c'est la ligne qui dit laquelle, pas l'onglet). Le tri se fait sur **l'état de l'affaire**, jamais sur `contacts.type` : l'état ne peut pas mentir, alors que le type est une saisie qui peut rester en arrière — c'est précisément ce qui s'était produit le 18/09, un contact qualifié restant « Prospect » et n'apparaissant donc plus nulle part. `promouvoirClient()` tient quand même `type` à jour, pour la fiche et pour les autres écrans. La pile montre **Reçu · Origine · Demande · Client · RDV téléphonique · Chargé d'affaires** : pas de coordonnées, elles sont dans la fiche du contact qu'un clic sur la ligne ouvre. L'**origine** se lit sur l'affaire et se dit en cinq mots : **Site internet · En direct · Partenaire (+ nom) · Meta Ads · Recommandation client**. L'apporteur nommé passe avant tout (« Partenaire · Cabinet Loreau », « Courtier · Crédit Azur ») ; sinon le canal CRM est traduit par `ORIGINE_PAR_CANAL` (`schema.js`), et un canal absent de la table tombe dans « En direct ». Les treize canaux servent à la **saisie**, cette table à la **lecture** : ne pas afficher le canal brut, et ne jamais déduire l'origine du canal du **contact** — c'est celui de l'affaire qui fait foi. Le libellé exact reste en infobulle. Un bouton **✉** prépare le message de transmission au chargé d'affaires (`mailTransfert`) : le CRM n'a jamais reçu le mail de confirmation, il ne peut donc rien « faire suivre » — il compose un `mailto:` pré-adressé portant les mêmes informations, que la personne envoie depuis sa messagerie. Rien ne part sans un clic, et aucun serveur de mail n'est nécessaire. Le **RDV téléphonique** vient de la **tâche** de type `rdv` (`due_date` + `due_time`), pas de `fields.date_visite` qui ne porte que le jour ; l'heure est signalée en rouge quand elle est passée et le lead toujours dans la pile, et « À planifier » quand il n'y a pas de rendez-vous. **Ce n'est pas « sans responsable »** : un lead déjà attribué reste un nouveau lead tant que l'appel n'a pas eu lieu, et c'est bien ce qu'on veut suivre. Le **chargé d'affaires se choisit dans la liste**, colonne placée juste après le nom, dans la pile comme dans le listing des contacts (`choixResponsable()`) — sélecteur pour la direction, texte simple pour les autres, `—` quand aucune affaire n'est rattachée. L'attribution passe par `assignerResponsable()` de `deal.js`, partagée avec le bouton de la fiche d'affaire : les trois chemins doivent produire le même résultat, trace comprise ; `js/pages/courtage.js` ceux de La Référence Courtage (`#/courtage`, `/base`, `/vivier`). Ces structures sont les lignes du menu Pilotage listées par `ESPACES` dans `js/app.js` : elles ouvrent leur espace au lieu de leur pipeline ; les pipelines restent joignables à `#/pipeline/<clé>`.
- Coquille commune à ces espaces : `js/pages/espace.js` — `coquilleEspace()` (menu vertical à gauche sur `--accent-ink`, en-tête et contenu à droite : la présentation du tableau de bord RGD Renova, aux couleurs de la structure), `poserEspace()` et `kpiEspace()`. Classes CSS `.esp-*` ; celles en `.btp-*` qui restent sont les écrans propres au cabinet BTP (agenda, DTU, mails types). La barre du CRM n'ayant que deux niveaux, c'est cette coquille qui porte la navigation interne ; `.content.flush` + `.esp-app { flex: 1 }` lui laisse toute la surface, et `body:has(.esp-app)` masque la date en double du CRM. Le grand chiffre d'un indicateur prend `--accent-ink`, pas `--accent` : certaines couleurs de marque sont trop claires sur blanc.
- Vivier courtiers (`js/pages/vivier.js`) : c'est le recrutement de La Référence Courtage, donc un écran de son espace (`#/courtage/vivier`) et non un univers du CRM. `vivierPage` est rendu tel quel dans le `.esp-body` de la coquille ; l'ancienne adresse `#/vivier` redirige.
- `js/data/db.js` — accès données (Supabase ou local). **Supabase renvoie 1000 lignes max par requête : le chargement est paginé avec `.range()`, ne pas retirer.**
- `js/data/scope.js` — droits côté client (les mêmes règles sont imposées côté serveur par les policies RLS ; les deux doivent rester cohérentes).
- `js/data/finance.js` — calculs de prêts (échéancier, différé partiel/total, CRD, mensualité imposée), types et statuts de biens.
- `js/data/schema.js` — activités, rôles, étapes de pipeline.
- `js/data/chiffres.js` — **tous les indicateurs de pilotage passent par ici** : leads, RDV, signatures, CA, entonnoir, objectifs. Le tableau de bord (`#/home`) et la vue d'ensemble (`#/dashboard`) lisent cette source unique ; deux écrans qui montrent « le CA de septembre » doivent montrer le même nombre. L'entonnoir repose sur cinq jalons communs aux quatre pipelines (reçus → contactés → RDV via `reachedRdv` → proposition à `p >= 55` → gagné), et les taux de conversion se lisent sur cette même cohorte : ne pas recalculer un taux à partir de deux populations différentes.
- **Le mot « signé » a disparu des libellés de CA** : chaque outil applique sa définition (le tableau de bord RGD envoie du CA **facturé**, pas signé). L'écran dit « CA HT » et la mention de source rappelle que les définitions diffèrent d'une structure à l'autre — ne pas réintroduire un qualificatif que toutes les sources ne respectent pas.
- **CA prévisionnel de BTP Expertise** : le tableau de bord du cabinet ne compte plus le CA à partir des étapes de réalisation (`delivery`) mais à partir de **l'engagement du client** — « Lettre de mission » côté expertise, « Mission AMO signée » (clé `amo_contrat`) côté AMO. Le seuil est déclaré une fois sur l'activité (`ACTIVITIES.btp.engagement = { expertise, amo }` dans `schema.js`) et lu par `estEngagee()` ; le rang se compare **dans la liste du métier**, jamais dans la liste complète des étapes — celles de l'AMO suivent celles de l'expertise dans le tableau, les indices des deux ne sont pas comparables. Une affaire perdue ne compte plus, une affaire encore aux étapes communes (avant l'entretien) n'a pas de métier donc pas d'engagement, et tout ce qui suit le seuil dans le déroulé reste compté : on n'enlève pas du prévisionnel une mission qui avance. La tuile est placée **à droite de « Missions en cours »**, et les deux ne disent pas la même chose (« en cours » = étapes de réalisation, « engagées » = à partir du seuil) : c'est voulu. « Prévisionnel » n'est pas « facturé » — la facturation a son propre écran.
- **La réalisation ne commence pas au même endroit dans les deux métiers.** Côté expertise, « Lettre de mission » est une proposition : la réalisation démarre au **RDV sur place**. Côté AMO, la **« Mission AMO signée »** (clé `amo_contrat`) est déjà un engagement ferme : elle porte donc `delivery: true` et `p: 100`, et tout ce qui suit jusqu'à « Réception chantiers » est de la réalisation. Le commentaire de `stages` l'énonçait depuis l'origine (« ou du contrat signé (AMO) ») mais le drapeau ne commençait qu'à l'étape suivante — écart corrigé le 19/09/2026. Conséquences voulues : une AMO signée compte dans « Missions en cours » et devient **facturable**. **Elle n'est pas gagnée pour autant** — voir ci-dessous. Ne pas confondre `delivery` avec `engagement` : le premier dit que le travail commence, le second où démarre le CA prévisionnel — ils coïncident en AMO, pas en expertise, et chacun a sa déclaration.
- **Chez BTP Expertise, gagner une affaire est un GESTE, pas une conséquence.** Aucune étape ne déclenche le gain : arriver à « Réception chantiers » ne veut pas dire que la réception est faite, arriver à « Clôturé facturé » ne veut pas dire que la facture est réglée. C'est la direction ou le chargé d'affaires qui déclare l'affaire gagnée, avec **« 🎉 Marquer gagnée »** (`setWon`), une fois ce dernier travail terminé. Arbitré le 19/09/2026 — ne pas rétablir un gain automatique sur une étape. `ACTIVITIES.btp.gain = { expertise: 'rdv_complementaire', amo: 'amo_reception' }` ne déclare donc **pas** une étape gagnante mais **la dernière étape du déroulé** : `estEtapeFinale()` la reconnaît, `etapeFinale()` dit où `setWon` doit poser l'affaire. Une activité qui ne déclare pas `gain` garde l'ancienne règle, où toute étape de réalisation gagne : c'est le cas de Propulsion (`onboarding`), et les trois autres pipelines ne bougent pas. **Le recul reste automatique**, lui : `moveStage` **rouvre** l'affaire (`status`, `won_at`, `closed_at`) dès qu'elle quitte sa dernière étape, et l'inscrit dans l'historique — gagner est une décision, ne plus l'être est une conséquence, sinon le CA compterait une victoire qui n'a plus lieu.
- **Trois seuils cohabitent sur le même déroulé et ne se confondent jamais** : `engagement` (le CA prévisionnel démarre), `delivery` (le travail commence, la mission devient facturable), `gain` (la dernière étape, où une affaire gagnée se tient). **« Missions en cours » ne compte que les affaires `open` à une étape de réalisation** : une mission gagnée est finie, elle sort du compteur et **libère sa charge** — `chargeDe()` ne compte que les ouvertes, pour la même raison. Elle **reste visible** dans sa colonne du pipeline (`vivantes()` garde les gagnées) : une affaire ne doit pas disparaître d'un écran parce qu'elle s'est bien terminée. Ces deux listes répondent à deux questions différentes — ce qui m'occupe, et ce que je dois voir — ne pas les fusionner.
- **L'étape `rdv1` de BTP Expertise s'affiche « RDV tel »** (elle s'appelait « RDV 1 »). **La clé ne change pas** : elle est écrite par `creer_prospect_btp`, et `lead`/`rdv1` doivent rester les deux premières étapes de la liste sous peine de fausser `reachedRdv()` et `avantEntretien`.
- **Changer de métier, c'est changer de pipeline.** Chez BTP Expertise chaque étape appartient à l'expertise **ou** à l'AMO. Basculer `fields.type_mission` sans toucher à `stage` laissait l'affaire à une étape de l'autre métier : `pipelineDe()` la comptait dans `siennes` (donc dans « n missions en cours · X € de CA potentiel ») mais **aucune colonne ne l'accueillait**, et `estEngagee()` ne la trouvait pas non plus — elle disparaissait du pipeline et du CA prévisionnel sans un mot. Constaté en production le 19/09/2026 sur une mission passée en AMO alors qu'elle était à l'étape `qualifie`. Deux réponses, à garder toutes les deux. **Prévenir** : `etapeEquivalente(activity, stage, mission)` (`schema.js`) traduit une étape d'un métier vers l'autre **par le rang** dans la liste du métier — les deux déroulés se répondent un à un, donc aucune table de correspondance à tenir (elle se périmerait au premier renommage) ; `dealForm` l'appelle à l'enregistrement, replace l'étape, complète `stage_history` et **inscrit le changement dans `events`** en nommant les deux métiers — sans quoi l'historique dirait « Qualifié » remplacé par « Qualifié », les deux métiers ayant des étapes homonymes. **Détecter** : `pipelineDe()` renvoie `egarees`, et l'écran du métier affiche un encadré ambre les listant, avec un bouton « Replacer dans … » qui passe par `moveStage`. Une affaire ne doit jamais sortir d'un écran en silence ; si le cas se reproduit par un autre chemin, il se verra.
- **Ce qui fait qu'un client est « apporté par le chargé d'affaires ».** Rien à cocher : c'est l'**origine du lead** choisie sur la fiche découverte (expertise comme AMO), déjà écrite sur l'affaire dans `deals.channel`. Deux canaux valent apport — **« Recommandation client »** et **« Prospection directe »** —, déclarés par `REMUNERATION_BTP.origines[…].canaux` dans `schema.js` et lus par `cleRemuneration(deal)` ; tous les autres décrivent un lead venu au cabinet (site, publicité, partenaire, appel entrant, ancien client) et **retombent sur la clé du cabinet** : on n'attribue jamais un apport par défaut, y compris pour un canal inconnu ou vide. Arbitré le 18/09/2026. `partChargeAffaires(deal)` applique la clé **affaire par affaire** — jamais un pourcentage moyen sur un total, les deux clés cohabitent dans un même portefeuille. Le tableau de bord ajoute la part sous les deux chiffres de CA **pour un chargé d'affaires seulement** (`note` de `kpiEspace`, deuxième ligne facultative) : « dont X € pour vous » sur l'encaissé, « **≈** X € pour vous, **une fois encaissé** » sur le prévisionnel — le manuel (§13) paie la part sur les sommes encaissées, pas sur les montants facturés, et le libellé ne doit pas laisser croire à un dû. La direction ne voit pas cette ligne : ses tuiles sont celles du cabinet entier.
- **CA encaissé, et ce que le chargé d'affaires ne voit pas.** La quatrième tuile du tableau de bord BTP était « Charge du réseau » ; c'est désormais **« CA encaissé »**. La charge sert à répartir les leads, pas à travailler un dossier : elle ne regarde que la direction, qui la retrouve entière dans la carte « Charge des chargés d'affaires » — **masquée pour les autres**, la répartition du CA prenant alors toute la largeur (`.btp-duo-seul`). L'encaissé lit la **même définition que l'écran Facturation** : `encaissees(annee)` et `sommeMontants()` (`btp.js`), remontées près de `chargeDe()` pour que les deux écrans partagent le calcul au lieu de le recopier — c'est la date de **paiement** qui date l'encaissement, pas celle de la facture, et une mission sans `fields.paiement_date` ne compte pas. Les deux tuiles de CA sont les deux bouts de la même mission : **prévisionnel** = promis (à partir de l'engagement), **encaissé** = rentré (payé dans l'année). **Ce sont des montants de mission, jamais une part de rémunération** : la clé 55/45 ou 65/35 de `REMUNERATION_BTP` ne s'applique nulle part sur ces chiffres, elle ne vit que dans l'écran « Chargés d'affaires » (les deux clés étaient 60/40 et 70/30 jusqu'au 20/09/2026 ; elles ne sont écrites qu'une fois, dans `schema.js`). Un chargé d'affaires voit ces tuiles calculées **sur ses seuls dossiers** (la RLS filtre par `owner_id`), la direction sur tout le cabinet : même définition, population différente. Même partage sur l'écran **`#/btp/charges`** : la direction voit « Le réseau » entier, avec « + Chargé d'affaires » et le crayon de chaque fiche ; un chargé d'affaires voit « Ma charge », **sa seule ligne** (`f.profile_id === scope.user.id`), sans bouton de création ni crayon — la capacité et l'objectif sont réglés par la direction. Il garde en revanche tout le reste de l'écran, et c'est la raison pour laquelle on ne le lui a pas fermé : barème de points par métier, règles de capacité, **grille de rémunération** et fiche métier le concernent directement. **L'écran est le miroir exact des policies, pas un simple habillage** : `btp_charges_read` a été resserrée le 18/09/2026 (migration `20260918220000_charges_lecture_cloisonnee`, recette puis production) et ne rend plus que `my_role() = 'direction' or profile_id = auth.uid()` — la table elle-même ne renvoie qu'une ligne à un chargé d'affaires, l'API comprise. `btp_charges_write` reste à la direction seule, ce que le crayon masqué reflète. **Conséquence assumée** : une fiche sans `profile_id` (quelqu'un inscrit avant d'avoir un compte CRM) n'est lisible que par la direction. Cette table n'est lue que par cet écran — le tableau de bord calcule la charge depuis `deals.owner_id`, pas depuis elle.
- **Objectifs de CA** : **annuels**, stockés dans `settings` (clé `objectifs_ca`, JSON `{periode:'annuel', rgd: 480000, …, mois: {"2026-09": {rgd: 52000}}}`), donc sans nouvelle table — lecture pour tous, écriture direction, les policies existent déjà. Une période faite de mois entiers prend un douzième par mois (pas de prorata par jours : un objectif annuel de 480 000 € vaut 40 000 € en février comme en juillet) ; une journée ou une semaine est proratisée sur l'année ; au-delà de dix-huit mois, pas d'objectif. Un enregistrement sans `periode` date de la saisie mensuelle et est relu comme tel : ne pas inverser ce défaut. Le repère sur la jauge marque la part de période écoulée — un pourcentage d'objectif seul ne veut rien dire le 3 du mois.
- **Objectifs du cabinet, au-dessus des deux pipelines de missions** (`#/btp/expertise` et `#/btp/amo`). Les jalons suivis sont déclarés une fois, dans `ACTIVITIES.btp.objectifs` (`schema.js`) : Leads · Qualifiés · RDV terrain · Missions signées (€). **Chaque jalon nomme une étape PAR MÉTIER**, jamais une seule pour les deux — « Qualifié » est `qualifie` en expertise et `amo_cadrage` en AMO, le RDV terrain `rdv` d'un côté et `amo_programme` de l'autre ; `aAtteint()` compare les rangs **dans la liste du métier**, jamais dans la liste fusionnée, pour la raison qui piège déjà `estEngagee()`. **L'objectif est celui du CABINET, pas du métier affiché** : un lead arrive avant qu'on sache s'il deviendra une expertise ou une AMO (les étapes `lead` et `rdv1` sont communes, et `missionDe()` répond « expertise » par défaut), donc un découpage par métier mettrait presque tous les leads d'un côté. Le même bloc, les mêmes chiffres, sur les deux écrans. **Tous les jalons se lisent sur la MÊME COHORTE** — les affaires créées dans la période —, sinon les taux de passage ne veulent rien dire ; seul le CA fait exception, c'est celui **signé** sur la période quelle que soit la date d'arrivée du dossier, et il n'a donc pas de taux. **Deux conventions de stockage cohabitent, et c'est assumé** : les volumes sont saisis et stockés **au mois** (`settings`, clé `objectifs_volume`, `{ btp: { leads, qualifie, rdv } }`), le CA reste **annuel** dans `objectifs_ca` — le redemander ici donnerait deux vérités sur le CA de BTP Expertise. Le formulaire ne parle que de mois et réécrit le douzième-inverse dans l'annuel : une seule convention pour l'utilisateur, une seule source par chiffre. Aucune table ni colonne nouvelle, donc rien à faire côté RLS — les policies de `settings` (lecture pour tous, écriture direction) couvrent déjà la clé, et le bouton « Régler » n'apparaît qu'à la direction, en miroir. **Le réglage accepte le nombre OU le taux de passage**, et l'autre se recalcule : c'est la même grandeur vue de deux façons (« 12 qualifiés » ou « 60 % des leads »). **Seul le nombre est enregistré** — un taux stocké à côté ferait une seconde vérité. ⚠ **Un taux relie deux grandeurs de même nature** : la ligne du CA n'en a pas, « 12 000 € rapportés à 10 RDV » est un panier moyen, dit en clair sous le formulaire. **La période se choisit de trois façons** : les trois raccourcis (Mois · Trimestre · Année), les flèches `‹ ›` qui reculent ou avancent d'un cran dans la même échelle (avec un retour « aujourd'hui » dès qu'on s'est décalé), et le mode **Dates** qui ouvre deux bornes. `plageObjectifs()` rend la plage, `libellePlage()` la nomme. ⚠ **La fin est EXCLUE**, comme partout ailleurs (`inRange` teste `t < end`) : une saisie « au 30 septembre » se termine donc au 1er octobre, sinon tout ce qui s'est passé le 30 disparaîtrait sans que personne le voie. Une plage faite de mois entiers prend l'objectif entier par mois ; toute autre durée est **proratisée**, volumes et CA par la même formule — quinze jours valent la moitié d'un mois. Une fin antérieure au début ne devine rien : la carte le dit et n'affiche aucun chiffre. Le choix (échelle, décalage et bornes) est mémorisé dans `localStorage` sous `crm_btp_objectifs_periode` — une préférence d'écran, pas une donnée ; une ancienne valeur seule s'y relit encore. Styles préfixés `.obj-` ; le repère sur la jauge marque la part de période écoulée, comme sur le tableau de bord du groupe.
- **Chiffres venus de l'extérieur** : la table `structure_stats` (lot 11) reçoit, par structure, le nombre de prospects et le CA HT mensuel poussés par l'outil qui pilote réellement l'activité (aujourd'hui le tableau de bord RGD Renova, via la fonction `push_structure_stats` protégée par le réglage `stats_token`). La vue d'ensemble (`js/pages/dashboard.js`) affiche ces chiffres **à la place** de son calcul interne dès qu'ils existent, et retombe seule sur ses propres données sinon. Un chiffre a une source et une seule : ne pas mélanger CA externe et compte d'affaires interne (le panier moyen affiche « — » tant que l'outil externe n'envoie pas aussi `deals`). Même règle pour les leads : `prospects` est un **total** sans date d'arrivée, donc la tuile « Leads » l'affiche tel quel et n'annonce ni évolution ni ventilation par mois. Dès que l'outil externe pose `leads` à côté de `amount` dans chaque mois de `revenue`, le CRM bascule sur cette ventilation et retrouve l'évolution et la courbe. Même mécanisme pour l'entonnoir et les RDV : un mois peut porter `contacted`, `rdv` et `quotes` ; sans eux la structure est exclue du « Pipeline & conversion » et la carte le dit, plutôt que de laisser croire à un entonnoir vide (`structuresHorsEntonnoir`). **Deux descriptions du parcours coexistent, et elles ne se mélangent pas.** `funnel` par mois — `{leads, rdv, quotes, signed}` — est **la cohorte** : parmi les prospects arrivés ce mois-là, combien ont atteint chaque statut depuis. C'est le vrai entonnoir, décroissant par construction, et il prime. Les compteurs à plat `rdv`/`quotes`/`deals` sont **des flux** : ce qui s'est passé pendant le mois, quelle que soit la date d'arrivée — utiles, mais ils font remonter les étapes. `deals` reste le nombre d'affaires signées dans le mois et sert au panier moyen : ne jamais le transformer en jalon de cohorte, d'où le jalon final nommé `signed`. **Chaque jalon est facultatif et indépendant** : un outil qui ne sait pas dater le premier contact n'envoie pas `contacted`, et l'étape **disparaît** de l'entonnoir au lieu d'y figurer à zéro (de même pour un jalon que seule une partie des structures compte et qui vaut zéro). L'entonnoir n'a donc pas toujours cinq étapes : **chercher un jalon par son `champ`, jamais par sa position** — c'est ainsi que les taux de conversion se lisent. **Un entonnoir alimenté par des compteurs mensuels n'est pas forcément décroissant** — un prospect de juin contacté en août compte dans les « contactés » d'août sans être dans ses « leads ». La carte affiche alors `↑` au lieu d'un taux de passage absurde et prévient que les étapes ne suivent pas la même cohorte : ne pas « corriger » cela en plafonnant les chiffres, c'est la donnée qui parle.

Les expertises gardent leurs champs manuels (`fields.facture_num`, `facture_date`, `paiement_date`) et passeront sur **Stripe** ; RGD Renova, La Référence Courtage et Propulsion ne sont pas concernées. **Le navigateur ne connaît aucune clé** : il appelle l'Edge Function `henrri-amo` (dépôt backend), qui porte le secret — rangé dans le coffre de la base, jamais dans `settings`, lisible par tout utilisateur authentifié. La fonction **refait la vérification des droits côté serveur** en relisant l'affaire avec le jeton de l'appelant, à travers la RLS : elle écrit ensuite en `service_role`, qui contourne la RLS, donc elle ne peut pas s'en remettre à l'écran. La table `henrri_documents` **n'a aucune policy d'écriture** — ce qui s'affiche vient de Henrri et de lui seul, le CRM ne peut pas mentir dessus. **L'état est distant, donc lu après le rendu** : `openDeal` garde `etatCourant` à côté de la fiche et redessine quand la réponse arrive ; le rendu étant synchrone, il ne peut pas l'attendre. **Le « reste à encaisser » se calcule à l'affichage** (`totauxHenrri`), jamais en base : il se périmerait au premier règlement. ⚠ **Les trois tuiles d'argent affichent le HT en grand et le TTC en dessous**, jamais l'inverse et jamais un mélange : « Facturé 3 500 » à côté de « Encaissé 0 » et « Reste 4 200 » se lit comme une erreur de calcul alors que le premier chiffre était HT et les autres TTC (constaté le 19/09/2026). Le HT est celui qui se compare au montant de la mission ; le TTC, juste dessous, est ce qui entre en banque. `totauxHenrri` rend donc les deux pour chacun (`ht`/`ttc`, `encaisseHt`/`encaisseTtc`, `resteHt`/`resteTtc`) — ne pas réintroduire un total unique, c'est ce qui avait fait mélanger les unités. ⚠ **Sans la portée « Payment » chez Henrri, l'encaissé est un tout ou rien** : une facture à moitié réglée compte pour zéro, et le bloc le dit au lieu de le masquer. **Le bouton « Ouvrir » demande le lien au clic** : Henrri ne rend qu'une URL de PDF temporaire, la stocker donnerait un lien mort ; le numéro de document venant de l'écran, la fonction vérifie d'abord qu'il appartient bien à **cette mission** et à **cet environnement** avant de le présenter à Henrri (`documentDeCetteMission`, partagée avec « Finaliser »). ⚠ **C'est la seule route Henrri qui ne répond pas** : `POST /v1/documents/{id}/pdf/url` reste pendue — ni en 12 s ni en 30 s, sur un brouillon comme sur une facture finalisée —, alors que le `GET` du même chemin rend 405 en 10 ms, donc la route existe et le verbe est bon (constaté en recette le 19/09/2026). D'où un **délai maximal de 20 s sur TOUS les appels Henrri** (`DELAI_HENRRI_MS`, posé sur `henrri()` **et** sur l'authentification) : un appel qui ne revient jamais est pire qu'un appel qui échoue — sans lui la fonction attendait d'être coupée par la plateforme et l'écran tournait sans un mot. Le bouton dit « Ouverture… » pendant l'attente, sinon vingt secondes de bouton grisé ressemblent à une application figée. Les appels normaux reviennent en 60 à 1 500 ms : le délai ne gêne personne. **Un document naît en brouillon** — numéro non définitif, encore modifiable : le bouton **« Finaliser »** le fige chez Henrri (`POST /v1/documents/{id}/finalize`, sans corps) et disparaît ensuite, puisqu'il n'y a plus rien à figer. Le geste est **irréversible** (« once finalized the document cannot be edited anymore ») et coûte 2 à 8 crédits en production, d'où la confirmation à l'écran ; le numéro et le statut sont ensuite **relus chez Henrri**, jamais déduits. ⚠ **`/validate` n'est pas l'étape d'avant** : malgré son nom, cette route enregistre l'**acceptation du devis par le client** et exige son nom, son adresse et son IP — les fabriquer serait inventer un consentement, le CRM ne l'appelle pas. **Une mission AMO se facture en TROIS FOIS** — 40 % **à la signature** (`amo_contrat`), 40 % au suivi intermédiaire, 20 % à la réception (arbitré le 19/09/2026 ; l'acompte partait d'abord du démarrage du chantier, ramené à la signature le même jour — entre les deux il y a la consultation des entreprises, que l'acompte est là pour couvrir). ⚠ **Les poids des six phases du manuel (`PHASES_AMO`, 10/15/20/35/15/5) ne sont PAS une clé de facturation** : le manuel V5 les présentait ainsi et l'écran `#/btp/amo` le répétait, ce qui donnait deux vérités dans la même application. Ils disent ce que chaque phase pèse ; l'échéancier seul dit quand et combien facturer, et l'écran le rappelle désormais. Les parts et l'étape qui débloque chacune sont déclarées une fois, dans `ACTIVITIES.btp.echeances.amo` (`schema.js`), à côté des étapes ; `echeancesDe(deal)` en tire les montants et dit lesquelles sont atteintes. **Le dernier montant est le RESTE, jamais un pourcentage** : 40 %, 40 % et 20 % arrondis chacun de leur côté ne retombent pas sur le total, et la somme des factures doit coller au centime au montant de la mission. Sur une AMO il n'y a donc **plus de bouton « + Facture » libre** — il appellerait le montant entier d'un clic, à côté de l'échéancier : on ne facture que depuis une ligne d'échéancier, et une échéance ne s'appelle **qu'une fois**. Ce verrou existe à trois niveaux, et les trois comptent : l'écran masque le bouton, la fonction refuse avant d'écrire chez Henrri, et un **index unique** (`idx_henrri_echeance_unique`, migration `20260919060000_henrri_echeances`) l'interdit en base — un écran et un contrôle applicatif se contournent, un index non. La colonne `henrri_documents.echeance` porte cette trace : **Henrri ne la connaît pas**, donc toute relecture (`rafraichir`, `finaliser`) doit la REPORTER, sinon l'échéancier rouvrirait une échéance déjà facturée. ⚠ **L'échéancier est écrit deux fois** : dans `schema.js` et dans l'Edge Function, qui ne peut pas importer un module du navigateur — et le montant ne peut pas venir de l'appelant, qui annonce la somme décide de la somme. La dérive est donc rattrapée à l'exécution : l'écran envoie le montant qu'il a **affiché**, le serveur refait le calcul et **refuse** si les deux diffèrent, en montrant les deux chiffres. Ne pas retirer ce garde-fou en croyant simplifier. **Le devis se transforme en facture** (`POST /v1/documents/{id}/transform-to-invoice`, bouton « → Facture » sur la ligne d'un devis **finalisé**) : Henrri crée la facture À PARTIR du devis, elle en garde le lien et le devis est marqué facturé — mieux qu'une facture créée à côté, qui ne sait pas d'où elle vient. ⚠ **Elle porte le montant ENTIER du devis** : ce n'est donc pas une étape de l'échéancier mais son **alternative** — une mission se facture soit en trois fois depuis l'échéancier, soit en une fois d'ici. On ne bloque ni ne devine : le pied de l'échéancier signale les **factures hors échéancier** et leur total, parce que c'est la seule chose qui permet de voir qu'une mission risque d'être facturée deux fois. Le bouton disparaît dès qu'une facture sans échéance existe — ce n'est pas un drapeau en base, c'est lu de ce qui existe, et Henrri refuserait de toute façon une seconde transformation. **Bac à sable et production ne se mélangent jamais** : toute lecture de documents filtre sur `environnement`, comme `henrri_client_env` le fait déjà sur la fiche client — sans ce filtre, les documents d'essai entreraient dans les totaux « Facturé » et « Reste à encaisser » le jour du passage en production Henrri. En mode démo le bloc s'affiche mais annonce qu'il n'est pas joignable — aucun appel n'est tenté. Détail de l'API, des refus rencontrés et de ce qu'ils imposent : `docs/HENRRI.md` du dépôt backend.

## Modèle de droits (profiles)
Colonnes : `role` (direction | propulsion | **charge_affaires**), `activities` (text[] parmi rgd, btp, courtage, propulsion), `patrimony_access`, `rental_access`, `active`.
- **`charge_affaires` s'appelait `commercial`** jusqu'au 18/09/2026, en base comme ici (`ROLES` dans `js/data/schema.js`, défaut de `scope.role`, jeu de démo). Le libellé affiché n'a pas changé — il disait déjà « Chargé d'affaires » —, seule la valeur stockée s'est alignée dessus. La contrainte `CHECK` de `profiles.role` n'accepte plus l'ancienne valeur : une clé de `ROLES` **est** une valeur admise par la base, les deux ne peuvent plus diverger.
- **Un lead entrant n'a pas de responsable, et c'est un choix.** `creer_prospect_btp` et `intake_lead` créent l'affaire sans `owner_id` : par la règle ci-dessous, elle n'est donc visible **que par la direction**, qui la distribue à la main. Arbitré le 18/09/2026 — ni responsable par défaut, ni attribution tournante. La conséquence est entièrement côté CRM : une affaire orpheline doit **se remarquer**, sinon elle est perdue. `marqueResponsable()` et `SANS_RESPONSABLE` (`js/ui.js`) portent cette mention « À attribuer » sur la carte du pipeline, dans sa vue liste, dans la base BTP et en tête de la fiche d'affaire, et le filtre par responsable propose « À attribuer (n) » tant qu'il en reste. Ne pas remplacer cette mention par un tiret : un tiret ne dit pas qu'il y a quelque chose à faire.
- **Distribuer, et pouvoir le relire ensuite.** `attribuerDeal()` (`js/pages/deal.js`) attribue une affaire depuis sa fiche, sans passer par le formulaire complet — bouton « 👤 Attribuer », **réservé à la direction**. Elle ne propose que les personnes qui portent l'activité de l'affaire, plus la direction. Deux effets à ne pas retirer : les **tâches sans destinataire** suivent le nouveau responsable (une tâche que personne ne porte est invisible elle aussi), tandis que celles déjà confiées à quelqu'un ne bougent pas ; et l'attribution **s'inscrit dans l'historique** (`events`), sinon plus personne ne peut dire qui a confié quoi ni quand.
- **L'historique d'une affaire doit montrer le travail, pas seulement les jalons.** `events` reçoit les changements d'étape, les gains et pertes, les notes, l'attribution, et — depuis le 18/09/2026 — **les tâches cochées** (`toggleActivity` dans `js/pages/activity.js`, qui écrit l'événement sur place : importer `deal.js` depuis là créerait un cycle). C'est ce qui permet à la direction de vérifier ce qu'un chargé d'affaires a fait d'un lead, étape par étape.
- **La restriction par personne repose sur `owner_id`, jamais sur le rôle.** Aucune policy RLS ne teste `charge_affaires` : un chargé d'affaires voit ses dossiers parce qu'il en est le `owner_id`. Le rôle ne sert qu'à ouvrir la vision totale (`direction`) et Propulsion (`propulsion`). C'est ce qui a rendu le renommage sans effet sur les droits — et c'est pourquoi il ne faut **pas** chercher à identifier une personne par `activities` : ce champ dit à quelles structures elle appartient, pas quels dossiers elle porte (piste étudiée, écartée).
- Patrimoine (biens, prix, valeurs, prêts) : `role='direction'` **et** `patrimony_access=true` uniquement (`has_patrimony()`).
- Gestion locative : `rental_access=true` quel que soit le rôle, ou direction+patrimoine (`has_rental()`). Ne voit les biens qu'à travers la vue allégée `v_properties_rental` (sans prix ni financement).
- Propulsion : `role='propulsion'` + `'propulsion'` dans `activities` → voit les affaires/contacts/organisations marqués Propulsion + les siens. La ligne « Propulsion » du menu est le pipeline sous « Pilotage ».
- Vivier courtiers : direction ou `courtage` dans `activities`.
- Documents : droits de l'entité parente (`can_document(entity_type, id)`).

## Modèles métier à respecter
- **Prêts** : `duration_months` = mois d'amortissement **hors** différé ; `deferral_months` + `deferral_type` (`partial` = intérêts payés, `total` = intérêts capitalisés) ; `monthly_payment` optionnel (mensualité imposée par la banque, prime sur le calcul) ; `start_date` = première échéance. Les 13 prêts en base ont été validés au centime contre les tableaux d'amortissement : ne pas changer les formules de `finance.js` sans re-vérifier.
- **Loyers** : une ligne `rent_payments` par (bail, mois `YYYY-MM`) avec `due`, `apl`, `tenant_paid`, `amount`, `mode`, `adjustment`, `note`. Reçu = `apl + tenant_paid` quand renseignés, sinon `amount`. Solde d'un bail au mois k = Σ (due − reçu + adjustment) sur les mois ≤ k (`balanceOf` dans `locatif.js`). `adjustment` sert à réconcilier avec l'ancien Excel : ne pas le recalculer ni le supprimer. `prepareMonth` crée les lignes du mois pour les baux actifs.
- **Ids déterministes** : les données importées utilisent uuid5 (namespace `6f1c2a7e-3b7d-4c1e-9a55-1f2e3d4c5b6a`, clés `prop|…`, `unit|…`, `lease|…`, `pay|leaseId|month`, `loan|slug|banque`) pour que les scripts soient rejouables (`on conflict do nothing`).
- Contacts : une seule table/écran avec bascule Personne / Entreprise (`kind`) ; l'ancien écran Organisations redirige vers Contacts.
- **Une fiche ne se supprime plus, elle s'archive.** `contacts.archived_at` et `organisations.archived_at` (migration `20260918190000_archivage_fiches`) — null = active. `archiverFiche()`, `restaurerFiche()` et `estActive()` vivent dans `js/pages/espace.js` ; **plus aucun `db.remove('contacts')` ni `db.remove('organisations')` dans le dépôt**, et les boutons 🗑 des bases BTP et Courtage comme des formulaires de fiche sont devenus « 🗄 Archiver ». Archiver ne touche à **rien d'autre** : affaires, tâches et historique restent en place, contrairement à l'ancienne suppression qui emportait la grappe entière — c'est pourquoi la restauration est immédiate et sans reconstruction. Une fiche archivée sort de **toutes** les listes actives (BTP et Courtage) et n'apparaît que dans l'onglet « Archivés ». Ce n'est pas une question de droits mais d'affichage : la RLS porte sur les lignes, pas sur les colonnes, donc `scope.contacts()` continue de tout renvoyer et c'est à l'écran de filtrer avec `estActive`. **La suppression définitive existe encore, mais elle appartient à la direction** : `supprimerDefinitivement()` (`espace.js`), proposée **dans toutes les listes de fiches** — base BTP (Clients, Dossiers clos, Partenaires, Courtiers, Archivés) et base Courtage. Elle emporte la grappe entière (affaires, tâches, historique) et le dit avant. Les formulaires de fiche, eux, n'offrent que « 🗄 Archiver » : une modale ouverte pour corriger un numéro n'est pas l'endroit d'un geste irréversible. `scope.canSupprimerFiche` est le **miroir exact** des policies `contacts_delete` / `orgs_delete` (migration `20260918200000_suppression_direction`), qui ne testent plus que `my_role() = 'direction'` : elles ouvraient encore la suppression à `owner_id = auth.uid()`, donc **un bouton retiré d'un écran n'est pas un droit retiré** — c'est la policy qui fait foi, l'écran évite seulement d'offrir un bouton qui échouerait. Archiver reste ouvert à tous : c'est un `UPDATE` de `archived_at`, pas un `DELETE`. **Limite connue** : les sélecteurs de contact des formulaires (fiche d'affaire, etc.) proposent encore les fiches archivées ; à filtrer le jour où ça gêne.

## Règles absolues
- Dépôt **public** : ne jamais committer de données personnelles ou financières (locataires, loyers, prêts, fichiers `*-PRIVE.sql`, exports Excel/PDF). Les scripts d'import privés se lancent à la main et restent hors dépôt.
- Ne jamais mettre la clé `service_role` Supabase dans le code ; seule la clé publishable/anon est dans `js/config.js`.
- **Le schéma Supabase ne se modifie plus depuis le SQL Editor en production.** Tables, colonnes, fonctions, policies, triggers, Storage : tout passe par les migrations versionnées du dépôt privé `Mickael-Rigaud/CRM-Groupe-Backend`, testées sur l'environnement de préproduction (`crm-groupe-staging`) avant la prod. Une session qui travaille ici écrit le SQL voulu, mais l'application se fait là-bas. Les écritures de **données** (corriger une ligne, effacer un jeu de test) ne sont pas concernées. **Au 18/09/2026 les deux environnements sont alignés** — 21 entrées au journal de chaque côté, 19 fichiers de migration ; l'historique des dérives et des rattrapages est dans `docs/JOURNAL.md` du dépôt backend.
- Toute nouvelle table ou colonne : RLS activée + policy, et mise à jour de `scope.js` en miroir.
- Pas de dépendance nouvelle nécessitant un build ; rester sur des modules ES chargés par le navigateur.
- Tester en mode démo (servir le dossier avec `python3 -m http.server`, vider `SUPABASE_URL` dans une copie de `config.js`) avant de pousser ; ne pas casser le mode démo.
- Un commit par sujet, message en français à l'impératif court (ex. « Fiche bien : baux en cours uniquement »).
