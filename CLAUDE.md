# CRM Groupe — consignes pour Claude Code

Application interne de Mickael Rigaud pour piloter 4 activités (RGD Renova, BTP Expertise, La Référence Courtage, Propulsion) + modules transverses (Patrimoine, Gestion locative, Acquisition). Langue de travail : **français** (code, commits, interface).

## Stack (gratuite, sans build)
- SPA vanilla JS en modules ES, routage par hash (`#/page/param`). Aucun bundler, aucun `npm install` : les fichiers sont servis tels quels.
- Hébergement : GitHub Pages sur ce dépôt (branche `main`, racine). Un push sur `main` = mise en production (délai 1–2 min, Ctrl+F5 côté navigateur).
- Backend : Supabase (projet `crm-groupe`, plan gratuit) — Auth, Postgres avec RLS, Storage (bucket privé `documents`, URLs signées 1 h). Client `supabase-js` chargé depuis esm.sh. Chart.js vendu dans `assets/`.
- Mode démo : si `SUPABASE_URL`/`SUPABASE_ANON_KEY` sont vides dans `js/config.js`, `db.js` bascule sur un adaptateur localStorage (`crm_local_v1`) avec un jeu d'exemple (`js/data/seed.js`). Utile pour tester sans toucher à la production.

## Arborescence
- `index.html` — coquille, charge `js/app.js`.
- `js/app.js` — login, mise en page, `NAV` (navigation horizontale : bande 1 = les univers, bande 2 = les écrans de l'univers ouvert ; une page peut demander `fullBleed: true` pour masquer la date et occuper la surface — cas de RGD Renova). `renderNav()` est appelée **avant** `page.render()` : une page qui pose des commandes dans `.topbar` (classe `.embed-actions`) les voit préservées d'un rendu à l'autre. `js/icons.js` — icônes SVG des univers.
- `js/pages/*.js` — une page par fichier ; `js/pages/index.js` fait la table `pages` nom → fonction.
- `js/pages/home.js` — tableau de bord du groupe : filtre par entité (mémorisé, clé `crm_home_filtre`), tuile « Leads » qui ouvre la base de prospects de la structure (`BASE_PROSPECTS` : RGD renvoie à `#/rgd/prospects`, soit « Clients & prospects → Prospects » de son application, BTP et Courtage à leur base, Propulsion à son pipeline ; en vue Groupe chaque pastille de la répartition ouvre la sienne), six indicateurs avec comparaison à la période précédente et micro-courbe sur 12 mois, entonnoir, objectifs, courbes de CA, journée, tâches, patrimoine et locatif. Styles préfixés `.tb-` dans `css/app.css`.
- Espaces par structure : `js/pages/rgd.js` affiche l'application RGD Renova (site à part, iframe plein écran, `CONFIG.RGD_DASHBOARD_URL`) ; `#/rgd/<clé>` ouvre un **écran interne** de cette application via `urlRgd()` et la table `CONFIG.RGD_VUES` — le CRM ne connaît pas le routage du tableau de bord RGD, donc chaque destination y est déclarée à la main (chemin, fragment `#/…` ou adresse complète) ; **une valeur vide ouvre l'accueil**, un lien pas encore renseigné ne casse donc rien ; `js/pages/btp.js` regroupe les écrans de BTP Expertise (`#/btp`, `/base`, `/dtu`, `/facturation`, `/mails`) ; `js/pages/courtage.js` ceux de La Référence Courtage (`#/courtage`, `/base`, `/vivier`). Ces structures sont les lignes du menu Pilotage listées par `ESPACES` dans `js/app.js` : elles ouvrent leur espace au lieu de leur pipeline ; les pipelines restent joignables à `#/pipeline/<clé>`.
- Coquille commune à ces espaces : `js/pages/espace.js` — `coquilleEspace()` (menu vertical à gauche sur `--accent-ink`, en-tête et contenu à droite : la présentation du tableau de bord RGD Renova, aux couleurs de la structure), `poserEspace()` et `kpiEspace()`. Classes CSS `.esp-*` ; celles en `.btp-*` qui restent sont les écrans propres au cabinet BTP (agenda, DTU, mails types). La barre du CRM n'ayant que deux niveaux, c'est cette coquille qui porte la navigation interne ; `.content.flush` + `.esp-app { flex: 1 }` lui laisse toute la surface, et `body:has(.esp-app)` masque la date en double du CRM. Le grand chiffre d'un indicateur prend `--accent-ink`, pas `--accent` : certaines couleurs de marque sont trop claires sur blanc.
- Vivier courtiers (`js/pages/vivier.js`) : c'est le recrutement de La Référence Courtage, donc un écran de son espace (`#/courtage/vivier`) et non un univers du CRM. `vivierPage` est rendu tel quel dans le `.esp-body` de la coquille ; l'ancienne adresse `#/vivier` redirige.
- `js/data/db.js` — accès données (Supabase ou local). **Supabase renvoie 1000 lignes max par requête : le chargement est paginé avec `.range()`, ne pas retirer.**
- `js/data/scope.js` — droits côté client (les mêmes règles sont imposées côté serveur par les policies RLS ; les deux doivent rester cohérentes).
- `js/data/finance.js` — calculs de prêts (échéancier, différé partiel/total, CRD, mensualité imposée), types et statuts de biens.
- `js/data/schema.js` — activités, rôles, étapes de pipeline.
- `js/data/chiffres.js` — **tous les indicateurs de pilotage passent par ici** : leads, RDV, signatures, CA, entonnoir, objectifs. Le tableau de bord (`#/home`) et la vue d'ensemble (`#/dashboard`) lisent cette source unique ; deux écrans qui montrent « le CA de septembre » doivent montrer le même nombre. L'entonnoir repose sur cinq jalons communs aux quatre pipelines (reçus → contactés → RDV via `reachedRdv` → proposition à `p >= 55` → gagné), et les taux de conversion se lisent sur cette même cohorte : ne pas recalculer un taux à partir de deux populations différentes.
- **Le mot « signé » a disparu des libellés de CA** : chaque outil applique sa définition (le tableau de bord RGD envoie du CA **facturé**, pas signé). L'écran dit « CA HT » et la mention de source rappelle que les définitions diffèrent d'une structure à l'autre — ne pas réintroduire un qualificatif que toutes les sources ne respectent pas.
- **Objectifs de CA** : **annuels**, stockés dans `settings` (clé `objectifs_ca`, JSON `{periode:'annuel', rgd: 480000, …, mois: {"2026-09": {rgd: 52000}}}`), donc sans nouvelle table — lecture pour tous, écriture direction, les policies existent déjà. Une période faite de mois entiers prend un douzième par mois (pas de prorata par jours : un objectif annuel de 480 000 € vaut 40 000 € en février comme en juillet) ; une journée ou une semaine est proratisée sur l'année ; au-delà de dix-huit mois, pas d'objectif. Un enregistrement sans `periode` date de la saisie mensuelle et est relu comme tel : ne pas inverser ce défaut. Le repère sur la jauge marque la part de période écoulée — un pourcentage d'objectif seul ne veut rien dire le 3 du mois.
- **Chiffres venus de l'extérieur** : la table `structure_stats` (lot 11) reçoit, par structure, le nombre de prospects et le CA HT mensuel poussés par l'outil qui pilote réellement l'activité (aujourd'hui le tableau de bord RGD Renova, via la fonction `push_structure_stats` protégée par le réglage `stats_token`). La vue d'ensemble (`js/pages/dashboard.js`) affiche ces chiffres **à la place** de son calcul interne dès qu'ils existent, et retombe seule sur ses propres données sinon. Un chiffre a une source et une seule : ne pas mélanger CA externe et compte d'affaires interne (le panier moyen affiche « — » tant que l'outil externe n'envoie pas aussi `deals`). Même règle pour les leads : `prospects` est un **total** sans date d'arrivée, donc la tuile « Leads » l'affiche tel quel et n'annonce ni évolution ni ventilation par mois. Dès que l'outil externe pose `leads` à côté de `amount` dans chaque mois de `revenue`, le CRM bascule sur cette ventilation et retrouve l'évolution et la courbe. Même mécanisme pour l'entonnoir et les RDV : un mois peut porter `contacted`, `rdv` et `quotes` ; sans eux la structure est exclue du « Pipeline & conversion » et la carte le dit, plutôt que de laisser croire à un entonnoir vide (`structuresHorsEntonnoir`). **Deux descriptions du parcours coexistent, et elles ne se mélangent pas.** `funnel` par mois — `{leads, rdv, quotes, signed}` — est **la cohorte** : parmi les prospects arrivés ce mois-là, combien ont atteint chaque statut depuis. C'est le vrai entonnoir, décroissant par construction, et il prime. Les compteurs à plat `rdv`/`quotes`/`deals` sont **des flux** : ce qui s'est passé pendant le mois, quelle que soit la date d'arrivée — utiles, mais ils font remonter les étapes. `deals` reste le nombre d'affaires signées dans le mois et sert au panier moyen : ne jamais le transformer en jalon de cohorte, d'où le jalon final nommé `signed`. **Chaque jalon est facultatif et indépendant** : un outil qui ne sait pas dater le premier contact n'envoie pas `contacted`, et l'étape **disparaît** de l'entonnoir au lieu d'y figurer à zéro (de même pour un jalon que seule une partie des structures compte et qui vaut zéro). L'entonnoir n'a donc pas toujours cinq étapes : **chercher un jalon par son `champ`, jamais par sa position** — c'est ainsi que les taux de conversion se lisent. **Un entonnoir alimenté par des compteurs mensuels n'est pas forcément décroissant** — un prospect de juin contacté en août compte dans les « contactés » d'août sans être dans ses « leads ». La carte affiche alors `↑` au lieu d'un taux de passage absurde et prévient que les étapes ne suivent pas la même cohorte : ne pas « corriger » cela en plafonnant les chiffres, c'est la donnée qui parle.
- `js/agenda.js` — identifiants des calendriers Google, un réglage par structure (`rgd_calendar_id`, `btp_calendar_id`, `courtage_calendar_id`, `propulsion_calendar_id` — le nom de celui de BTP est antérieur, ne pas le renommer). Fournit aussi le **cadre intégré** Google, désormais réservé à l'espace BTP et au repli du tableau de bord. **Le cadre n'accepte que les modes `WEEK`, `MONTH` et `AGENDA`** : pas de `DAY`, une valeur inconnue le fait retomber silencieusement sur le mois, et en mode `AGENDA` le paramètre `dates` ne borne pas la fin — c'est pourquoi il ne peut pas servir à afficher une journée.
- `js/google-agenda.js` — **lecture réelle des agendas**, sans serveur : Google Identity Services délivre au navigateur un jeton d'accès temporaire (portée `calendar.readonly`), puis l'API Calendar renvoie les événements. L'`ID client OAuth` est dans `settings` (clé `google_client_id`) ; il est **public par nature** — il désigne l'application, pas un compte — mais le jeton reste en mémoire : jamais dans localStorage, jamais en base. Chacun ne voit que les calendriers partagés avec SON compte Google ; un calendrier inaccessible est signalé à part plutôt que de faire passer la journée pour vide. La fenêtre de consentement ne s'ouvre que sur un clic (les navigateurs bloquent les popups non sollicitées). Sans `google_client_id`, « Ma journée » retombe sur le cadre intégré.
- `js/agenda-sync.js` — **l'agenda du groupe vit dans le CRM** : la table `agenda_events` (lot 12) est un reflet des calendriers Google, pas l'original — un rendez-vous se crée et se modifie dans Google. La direction, qui a accès aux calendriers, relève la journée quand elle ouvre le CRM ; tout le monde lit ensuite la table, **sans connexion Google**. La fonction `remplacer_agenda(jour, calendriers, evenements)` efface puis réécrit la journée dans la même transaction, pour qu'un rendez-vous annulé disparaisse vraiment ; elle ne touche que les calendriers passés en argument, et la synchronisation ignore ceux qu'elle n'a pas pu lire plutôt que de vider leur journée. Ids déterministes `<calendrier>|<id google>`.
- **« Ma journée »** (dans `home.js`) est dessinée par le CRM à partir de cette table : rendez-vous Google et tâches horodatées du CRM mélangés, triés, filet à la couleur de la structure, trait rouge sur l'heure courante, passés grisés. C'est le seul endroit où les deux sources se mélangent vraiment.
- `js/documents.js` — pièces jointes (Storage) par entité.
- `js/ui.js` — helpers de rendu (`renderForm` avec `hint`, modales, tableaux, `esc`) et **filtres partagés** : `terms`/`hit` (recherche insensible aux accents, tous les mots exigés), `searchInput`/`bindSearch`/`restoreFocus` (barre de recherche + curseur conservé après redraw), `pickState`/`pickInit`/`multiPick`/`pickChips`/`bindMultiPick` (sélecteur multiple recherchable, mémorisé en localStorage — clé `crm_locatif_props` pour les biens loués, `crm_patrimoine_props` pour le patrimoine). Toute nouvelle liste filtrable doit réutiliser ces helpers plutôt que refaire un `<select>` ou un `toLowerCase().includes()`.
- `css/app.css` — **identité de groupe neutre** : accent indigo propre à l'outil (`--accent`, `--accent-ink`), gris froids, Inter Tight (titres) + Inter (texte). La couleur des quatre marques ne sert qu'au repérage des activités (`ACTIVITIES` dans `js/data/schema.js`) ; vert / rouge / ambre restent réservés aux états. Tout passe par les variables `:root` : changer de teinte = changer `--accent`. Logos des structures dans `assets/logos/<clé>.png` (rgd, btp, courtage, propulsion), affichés dans le menu, pastille de couleur en repli si le fichier manque. **Couleur par structure** : sur un écran rattaché à une activité, `applyBrand()` (js/app.js) repeint `--accent`/`--accent-2`/`--accent-soft`/`--accent-ink` avec les valeurs `accent`/`accent2`/`soft`/`ink` de l'activité (`ACTIVITIES`) ; ailleurs, retour à l'indigo du groupe. `color` reste la couleur d'identité (pastilles, bordures), `accent` en est la version assombrie, lisible sous du texte blanc — ne pas confondre les deux.
- `supabase/*.sql` — **historique**, plus une procédure : ces lots (`schema.sql` → `modules-lot2.sql` → … → `lot11-stats-structures.sql`) sont ce qui a été posé à la main avant la mise en place des migrations. Ils restent la référence pour comprendre le schéma, mais on ne les rejoue plus en production.

## Modèle de droits (profiles)
Colonnes : `role` (direction | propulsion | commercial), `activities` (text[] parmi rgd, btp, courtage, propulsion), `patrimony_access`, `rental_access`, `active`.
- Patrimoine (biens, prix, valeurs, prêts) : `role='direction'` **et** `patrimony_access=true` uniquement (`has_patrimony()`).
- Gestion locative : `rental_access=true` quel que soit le rôle, ou direction+patrimoine (`has_rental()`). Ne voit les biens qu'à travers la vue allégée `v_properties_rental` (sans prix ni financement).
- Propulsion : `role='propulsion'` + `'propulsion'` dans `activities` → voit les affaires/contacts/organisations marqués Propulsion + les siens. La ligne « Propulsion » du menu est le pipeline sous « Pilotage ».
- Vivier courtiers : direction ou `courtage` dans `activities`.
- Documents : droits de l'entité parente (`can_document(entity_type, id)`).

## Modèles métier à respecter
- **Prêts** : `duration_months` = mois d'amortissement **hors** différé ; `deferral_months` + `deferral_type` (`partial` = intérêts payés, `total` = intérêts capitalisés) ; `monthly_payment` optionnel (mensualité imposée par la banque, prime sur le calcul) ; `start_date` = première échéance. Les 13 prêts en base ont été validés au centime contre les tableaux d'amortissement : ne pas changer les formules de `finance.js` sans re-vérifier.
- **Loyers** : une ligne `rent_payments` par (bail, mois `YYYY-MM`) avec `due`, `apl`, `tenant_paid`, `amount`, `mode`, `adjustment`, `note`. Reçu = `apl + tenant_paid` quand renseignés, sinon `amount`. Solde d'un bail au mois k = Σ (due − reçu + adjustment) sur les mois ≤ k (`balanceOf` dans `locatif.js`). `adjustment` sert à réconcilier avec l'ancien Excel : ne pas le recalculer ni le supprimer. `prepareMonth` crée les lignes du mois pour les baux actifs.
- **Ids déterministes** : les données importées utilisent uuid5 (namespace `6f1c2a7e-3b7d-4c1e-9a55-1f2e3d4c5b6a`, clés `prop|…`, `unit|…`, `lease|…`, `pay|leaseId|month`, `loan|slug|banque`) pour que les scripts soient rejouables (`on conflict do nothing`).
- Contacts : une seule table/écran avec bascule Personne / Entreprise (`kind`) ; l'ancien écran Organisations redirige vers Contacts.

## Règles absolues
- Dépôt **public** : ne jamais committer de données personnelles ou financières (locataires, loyers, prêts, fichiers `*-PRIVE.sql`, exports Excel/PDF). Les scripts d'import privés se lancent à la main et restent hors dépôt.
- Ne jamais mettre la clé `service_role` Supabase dans le code ; seule la clé publishable/anon est dans `js/config.js`.
- **Le schéma Supabase ne se modifie plus depuis le SQL Editor en production.** Tables, colonnes, fonctions, policies, triggers, Storage : tout passe par les migrations versionnées du dépôt privé `Mickael-Rigaud/CRM-Groupe-Backend`, testées sur l'environnement de préproduction avant la prod. Une session qui travaille ici écrit le SQL voulu, mais l'application se fait là-bas. Les écritures de **données** (corriger une ligne, effacer un jeu de test) ne sont pas concernées.
- Toute nouvelle table ou colonne : RLS activée + policy, et mise à jour de `scope.js` en miroir.
- Pas de dépendance nouvelle nécessitant un build ; rester sur des modules ES chargés par le navigateur.
- Tester en mode démo (servir le dossier avec `python3 -m http.server`, vider `SUPABASE_URL` dans une copie de `config.js`) avant de pousser ; ne pas casser le mode démo.
- Un commit par sujet, message en français à l'impératif court (ex. « Fiche bien : baux en cours uniquement »).
